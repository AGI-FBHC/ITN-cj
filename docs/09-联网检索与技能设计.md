# 联网检索与技能机制设计（提案）

> 状态：**设计提案，尚未实现**。写于 2026-10-14，供实现方（并行会话）按阶段落地。
> 起因：用户提出两条需求 —— ① 知识库欠缺时，agent 应当有**自主联网获取资料**的能力，且交互形式要贴合"一个 harness 软件"该有的样子；② 这个 harness 应当像 Codex 一样拥有 **skill** 能力，但不确定怎么内置最合适。

本文回答三件事：**边界怎么定、交互长什么样、分几步落地**。设计与现有实现严格对齐（工具协议、会话事件、引用自检、产物落盘都已就位），不引入插件运行时。

---

## 一、先定边界：这一条会改 PRODUCT.md

`PRODUCT.md` 现在写着：

> 不做联网检索：只用用户自己给的资料和用户自己的模型。

这条要改，否则实现和产品定义互相打脸。建议改成：

> **默认不联网**，只用用户自己给的资料和自己的模型。用户可**显式开启**联网检索：搜索与抓取都走用户自己配置的服务；
> 联网来源会标注**抓取时间**、缓存到本机，可审计、可删除、可离线复用。

为什么这样改仍然不是"第二个 ITN"：产品形态没变——单人、本地、不注册、不用我们的服务器；变的只是"资料来源"多了一种，而且**这一种由用户明确开启、明确授权、明确可见**。

三条不可让步的红线：

1. **不做静默联网**。任何一次对外请求，对话框里都要留下一条可展开的记录。
2. **来源分级且可溯源**。本地资料引用 `[n]`，网络来源引用 `[Wn]`，且网络来源必须带**抓取时间**（网页会变）。
3. **抓回来的东西落本机**。联网不是"一次性看一眼"，而是把网页变成你的资料（可搜、可引、可播、可删、可离线）。

## 二、内核侧：联网怎么接最省事

### 2.1 两个工具，不要更多

| 工具 | 作用 | 依赖 |
| --- | --- | --- |
| `web_fetch(url)` | 抓一个已知 URL 的正文 → 落本机 → 可被引用 | **零新依赖**（只要 HTTPS 出网） |
| `web_search(query, k)` | 搜索 → 返回候选（标题/URL/摘要/时间） | 需要用户配一个搜索服务 |

**第一版必须先有 `web_fetch`**：即使不配搜索服务，"用户贴一个链接让 agent 读"也是完整可用的能力，而且它把「联网 → 落本机 → 进引用体系」这条最关键的链路先打通。

### 2.2 复用已有代码，别重写

- **HTTPS 出网**：`core/src/llm/llm.cj` 里已经解决过 TLS SNI 的坑（`tls.serverName = Some(hostOf(url))`、ALPN http/1.1）。建议把这个客户端构造抽成一个小工具（例如 `core/src/tools/http_text.cj`），`web_fetch` 直接用它，**不要**复制一份改改。
- **HTML → 正文**：`core/src/kb/kb.cj` 里的 `htmlToText` 是第 9 轮为 HTML 资料写的，已经会去 `script`/`style`、把 `h1~h6` 变成 Markdown 标题。直接复用；再补一条启发式：能匹配到 `<article>` / `<main>` 就只取那一段，否则取全文。
- **落本机**：`<dataDir>/webcache/<sha1(url)>.md`，文件头写 YAML frontmatter（`url / title / fetchedAt / bytes / status`）。同一 URL 重复抓取时**覆盖并更新 fetchedAt**（这就是"重新抓取"）。
- **引用**：把抓回的页面**转成与知识库切片同构的记录**（`docPath = URL`、`docTitle = 页面标题`、`headingPath = "网络资料 · 抓取于 <时间>"`、`text = 正文`）。
  这样引用编号、出处列表、产物末尾的「资料来源」、课件播放器**全部自动复用**，不需要为联网再写一套引用逻辑。这是本方案最关键的一个实现建议。

### 2.3 搜索服务的 provider 抽象

不要在代码里内置任何一家的 Key（隐私、成本、滥用三条都不允许）。内置的是**适配器**：

| provider | 说明 |
| --- | --- |
| `tavily` / `brave` | 商业搜索 API，用户填自己的 Key |
| `searxng` | 用户自建的 SearXNG 实例（最贴合"自己的服务"） |
| `custom` | 任何返回 JSON 数组的 HTTP 接口：在设置里填 URL 模板 + 结果字段路径 |
| `model-native`（可选） | 有些模型服务自带联网；支持但不依赖，因为它对"引用可溯源"不友好 |

统一出口只有一句：`搜索词 → [{title, url, snippet, publishedAt}]`。

### 2.4 抓取的安全与体面

只允许 `http/https`；单页上限 2 MB；超时 15 s；重定向 ≤ 3；`content-type` 不是文本/HTML 就直接说明"这个类型暂时读不了（例如 PDF）"——
**这与第 9 轮"读不了的文件如实报出来"的态度一致：宁可说读不了，也不要假装读到了。**

### 2.5 知识库"欠缺"怎么判定（功能上最容易被含糊过去的一点）

不要靠感觉，用四个可实现的信号，**前两个提前判断、后两个事后兜底**：

| 信号 | 判据（建议默认值，可配） |
| --- | --- |
| 命中强度 | top1 相似度 < 阈值（向量模式）；或关键词模式命中数 < 2 |
| 覆盖度 | 问题里的关键词在命中切片正文中的覆盖率 < 50% |
| 模型自陈 | 系统提示要求"资料不足时先输出 `INSUFFICIENT`"，命中即视为不足 |
| 引用自检 | 生成后 `citationReport.citedParagraphs / paragraphs` < 50%（已有实现，直接复用） |

判定结果和依据都要**写进会话事件**（一条 `validation` 或专门的 `insufficient` 事件），界面上就能解释"我为什么说资料不够"。

## 三、交互设计（这一节是重点）

原则六条：

1. **联网是一个可见的动词**。每次对外请求都在对话里留一行可展开的记录（复用现有 `.tool-row` 样式）。
2. **默认问一句，可以升级为"以后都自动"**。自动时也要先亮出"我打算查什么"，并留一个「停」。
3. **授权范围必须说清楚**：只这一次 / 这个会话 / 以后都自动。
4. **不弹模态框**。全部用对话内的行内卡片（与现有 `.dialog`/`.tool-row` 一致），不打断阅读流。
5. **抓错能删、并入能撤**。抓回来的是一等公民，不是临时变量。
6. **回答里的引用分级**：`[1]` 是资料、`[W1]` 是网络；末尾分区列出，网络条目带抓取时间与原链接。

### 3.1 场景 A（核心）：知识库不够时的自主行为

```
用户提问
  ↓
retrieve（现状）
  ├─ 命中质量够 → 正常回答（现状，不变）
  └─ 命中质量差
        ↓
     联网是否已授权？
       ├─ 否 → 对话里插一张「资料不足」卡片（不弹窗）：
       │     你的资料里没找到能支撑这个问题的内容
       │     （命中最相关的 2 段，相关度偏低）
       │     [上网查一下] [只用手头资料回答] [换个问法] [去补充资料]
       │        └─ 首次点「上网查一下」→ 展开一段说明（把什么发给谁、结果会存本机）
       │              [只这一次] [以后都自动（可在设置里关）]
       └─ 是 → 直接进入联网，但先出现一条「计划行」（可停）：
              ⏺ 准备联网检索："提示词工程 2026 最新做法"（预计 3~5 条）  [停]
  ↓
web_search → 候选行（可展开）：
     每条：标题 · 域名 · 摘要 · 发布时间   [打开] [剔除]
     底部：[全部抓取] [只抓勾选的 3 条] [换关键词重搜]   （默认勾选条数在设置里配）
  ↓
web_fetch 逐篇 → 每篇一行：
     已存本机 · 《标题》 · example.com · 1.2 万字符   [预览] [删掉]
     失败要如实说：403 / 超时 / 正文为空 → 并给「换一个来源」
  ↓
生成回答：正文用 [1]（资料）与 [W1]（网络）标注；末尾
     「资料来源」：- [1] ……
     「网络来源」：- [W1] 标题 · 域名 · 抓取于 10-14 15:20 · 原链接
  ↓
收尾（对话里出现一张小卡片）：
     已存为网络资料（2 篇）。要并入「我的课程资料」吗？
     [并入并重建索引] [只留在本机网络资料里] [删掉这次的]
```

注意最后一步：**联网抓到的东西默认存本机但不自动并入知识库索引**——临时内容不该污染你的正式资料，由你点头才并入。并入后它可以离线检索、可以进讲义，这就是"知识库欠缺"会**逐步自愈**的机制。

### 3.2 场景 B：用户主动要求联网

- 输入框上方工具栏加一个 **联网开关**（会话级）：开启后这一轮允许 agent 用 web 工具；旁边小字写明"用你配置的搜索服务"。
- 支持显式指令：`/web 提示词工程最新做法`（直达场景 A 的联网分支，跳过询问）。
- 直接往输入框里**贴一个链接** → 自动识别为"读这一页"（走 `web_fetch`），这是最自然的一句话交互。

### 3.3 场景 C：联网内容的生命周期

- 「我的资源」新增分区 **「网络资料（已存本机）」**：可搜索、可按域名筛、可**播放**（复用课件播放器）、可删除、可**重新抓取**（显示上次抓取时间）。
- 「领域知识库」的索引状态里，标明当前索引**包含 N 篇网络资料**（可一键剔除全部网络资料并重建索引——"我只要我自己的资料"这条退路必须有）。
- 「会话记录」里联网步骤天然可见：`tool/call(web_search)` → `tool/result` → 每篇 `web_fetch`，可回看"它查了什么、拿到了什么"。

### 3.4 场景 D：设置里能管住它

新增两张设置卡片（放在现有「模型与接口」「数据与备份」旁边，风格一致）：

**联网**
- 总开关（默认关）
- 搜索服务：provider + Base URL + Key + [测试搜索]
- 每次最多抓几篇、默认勾选几条、单页大小上限、请求超时
- 域名黑白名单（例：只允许 `*.gov.cn`、禁止内网地址）
- 「资料不足时自动联网」开关（默认关）

**技能**（见第四节）
- 技能清单：名称、说明、来源（内置/我的）、需要的工具、是否需联网授权、启用开关
- [打开技能目录] [新建技能]（模板生成一个 SKILL.md）

### 3.5 交互细节（容易被忽略但决定手感）

- 联网行**不占用对话正文**：它是一行灰底小字，可折叠；不要把搜索结果整段塞进消息流。
- 抓取中显示实时耗时与已抓篇数（复用第 5 轮生成进度卡的做法），**可停**（复用第 8 轮的取消机制：`/api/agent/cancel`）。
- 任何"上网"动作前，界面上必须能看到**要去哪**（域名与查询词），这是信任的关键。
- 失败不要红屏：一行灰字 + [重试] [换来源]，和"读不了 PDF"那条提示同一档语气。

## 四、Skill 机制：怎么内置最合适

### 4.1 形态：纯文件，不做插件运行时

```
<dataDir>/skills/<id>/SKILL.md      # 用户自己的技能（可写）
<app>/skills/<id>/SKILL.md          # 随包内置（只读）
```

`SKILL.md` 前置元数据：

```yaml
---
name: web-research
title: 联网做专题研究
description: 当问题在本地资料里得不到支撑时，去网上检索、抓取并整理成可引用的小结
when_to_use: 用户问"最新/行业做法"，或检索命中很低
tools: [kb_search, web_search, web_fetch, save_note, save_artifact]
requires_consent: web
version: 1
---
（正文：分步骤的编排说明，Markdown，像一份操作手册）
```

### 4.2 三条设计决定（也是"内置最合适"的答案）

1. **渐进披露**：启动只把 `name/title/description/when_to_use` 放进系统提示（几十个技能也只占几百 token）；
   模型判断需要时再调 `skill_read(id)` 把正文读进上下文，并写一条事件（界面上能看到"读取技能：联网做专题研究"）。
   这正是 Codex 的做法，也是"功能与上下文预算"之间最省的选择。
2. **skill 只编排、不执行**：**第一版不允许 skill 自带脚本**。
   理由：能跑任意脚本等于"能在这台机器上执行任意代码"，与"本地可信工作台"的定位直接冲突；
   而我们要的表达力（先搜→筛→抓→引用→产出）用"提示词 + 已注册工具"完全够。
   真需要"能跑的东西"时，走**内核注册的具名动作**（`kb.index`、`artifact.write`…），参数有 schema——
   能力可以扩，**权限不能扩**：skill 的 `tools:` 之外的工具，内核执行前直接拒绝并写事件。
3. **授权与技能分开**：`requires_consent: web` 的技能，在联网未开启时**不可用**（UI 里灰掉并给"去设置开启"）。
   这样"我装了联网技能"和"我允许它联网"是两件事，用户不会因为装了个技能就被偷偷联网。

### 4.3 触发方式（三种，覆盖不同习惯）

| 方式 | 交互 | 适合 |
| --- | --- | --- |
| 显式选择 | 输入框打 `/` → 技能列表（复用第 10 轮 Ctrl+K 弹层组件，加"命令模式"）；或点工具栏的技能 chip | 我知道要干什么 |
| 语义自动 | 系统提示里有清单，模型自己 `skill_read` | 我不想管，让它自己挑 |
| 会话绑定 | 新建对话时选"用哪个技能"；会话栏上显示 chip | 一整段工作都按同一套流程走 |

无论哪种，**执行过程都落在会话事件里**（读了哪个技能、调了哪些工具），「会话记录」页可回看。

### 4.4 随包内置哪些技能

只内置 1 个**真技能** + 1 个模板，别塞一堆：

- `web-research`（联网做专题研究）：完整演示"检索 → 筛选 → 抓取 → 引用 → 落本机 → 产出小结"的编排。
  它的存在同时也是联网能力的**推荐入口**（用户不必自己写提示词）。
- `_template`（新建技能用的骨架）。

### 4.5 与"工具"的关系（一句话说清）

**工具是内核的能力（代码），技能是使用能力的说明书（文本）。**
加一个工具 = 内核升级；加一个技能 = 写一个 Markdown 文件。前者慢而稳，后者快而安全。

## 五、落地顺序（每阶段都能独立交付并验证）

| 阶段 | 内容 | 涉及文件（预计） | 验证方式 |
| --- | --- | --- | --- |
| **P1** | `web_fetch`（贴链接就能读 → 落本机 → 引用 `[W1]`）；设置页「联网」卡片只放总开关与域名黑白名单 | `core/src/tools/http_text.cj`(新)、`tools/web.cj`(新)、`tools/registry.cj`、`kb/kb.cj`(复用 htmlToText)、`api/api.cj`、`shell/renderer/app.js` | 本地起一个 mini HTTP 服务当"网页"；E2E 断言：抓取→正文入库→回答带 `[W1]`→资源页能看到→可删 |
| **P2** | `web_search` + provider 适配器（tavily/brave/searxng/custom）+ 「测试搜索」；候选卡片与勾选剔除 | 同上 + 设置页新增字段 | 用本地 mock 搜索服务；E2E 断言候选列表、剔除、只抓勾选项 |
| **P3** | 欠缺判定（四个信号）+「资料不足」卡片 + 三级授权（一次/会话/永久）+「计划行 + 停」；引用自检区分 `[n]`/`[Wn]`（扩展 `citationReport`） | `agent/agent.cj`、`api/api.cj`、`app.js` | 构造一个 KB 里没有的问题；断言卡片出现、"只用手头资料"走原路径、"上网查"才发请求；联网中可停 |
| **P4** | Skills：目录扫描 + 清单入提示 + `skill_read` + `/` 选择 + 设置页「技能」卡片 + 内置 `web-research` | `agent/skill.cj`(新)、`agent/agent.cj`、`api/api.cj`、`app.js` | fixture 技能：能被列出 / 能被读取 / **越权工具被拒**；用 `web-research` 跑通一次"查→抓→答→落" |

接口契约（`docs/02-接口契约.md`）在每阶段同步补：新增工具、`/api/web/*`（若需要单独触发抓取）、settings 里的联网字段、新的事件类型（`insufficient`、`skill/read`）。

## 六、需要拍板的 6 个决策点（附我的建议）

| # | 问题 | 我的建议 |
| --- | --- | --- |
| 1 | 资料不足时默认自动联网吗？ | **默认关**；首次询问时提供"以后都自动"，自动时仍亮出计划行并可停 |
| 2 | 内置哪些搜索 provider？ | Tavily / Brave / SearXNG / 自定义 四选一，**都不内置 Key** |
| 3 | 要不要支持"模型自带联网"？ | 支持（`model-native`）但不依赖——它对引用溯源不友好 |
| 4 | 抓回的内容默认去哪？ | **存本机 webcache，但不自动并入索引**；用户点头才"并入并重建索引" |
| 5 | skill 允许带脚本吗？ | **第一版不允许**；需要"能跑的动作"时走内核注册的具名动作 |
| 6 | 联网内容参与向量化吗？ | 只有"并入知识库"之后才参与；否则只在本次会话内可引用 |

## 七、明确不做（反模式清单）

- ❌ 静默联网（用户没点过任何按钮就外发请求）
- ❌ 把搜索结果整段灌进对话正文（污染阅读流；应该是一行可展开的记录）
- ❌ 联网内容自动进正式索引且不标注来源（会让"答案可溯源"当场破产）
- ❌ 递归爬取 / 全文镜像（法律与成本都不可接受）；只抓用户或模型选中的少数页面
- ❌ skill 执行任意脚本 / 读任意路径 / 访问未声明的工具
- ❌ 用我们的 Key 提供"免费搜索"（成本与滥用都不可控，且违背"用你自己的服务"）

## 七、知识网络 → 星云图（2026-10-14 用户给的规格）

> 目标：首页那张图从"章节节点 + 连边"升级成**一屏看懂所有知识库**的星云图：
> 中心一棵核，每个库一团星云，库间一线相连。**不引任何依赖**（自写 canvas 2D），
> 前端仍然只有 `index.html / app.js / style.css` 三个白名单文件。

### 视觉：一套调色板，两套背景

- **8 色调色板**（中间调：明度 60~75%、饱和 55~70%），按**库 id 哈希**分配；相邻库色相差 ≥40°。
  **色相在所有主题下不变**（只换背景与叠加方式）。
- 深色主题：深底；光晕用 `lighter` 叠加，halo alpha 0.35，连线 alpha 0.25。
- 浅色主题：浅底；光晕改 `source-over`，halo alpha 0.12，连线 alpha 0.45，点加 1px 同色深边
  （白底不靠发光也看得清）。
- 点：圆，半径 1.5~2.5px；**预渲染一张 64px 发光贴图**，所有点/光晕用 `drawImage` 缩放 + `globalAlpha`
  （不要每帧画几百个 `radialGradient`）。
- 呼吸：周期 4~8s，每点 phase 由 id 哈希决定（不同步才有星云感）；幅度 透明度 ±25%、半径 ±15%；
  位移只在绘制时 ±1.5px，**基础坐标保持稳定**。
- **不要自动旋转**（球壳惯性旋转的观感太游戏化）：改成呼吸 + 鼠标轻微视差，手动拖动保留。
- 状态只用亮度/外圈环表达：已读=实心、未读=空心、有错题=红环、有产物=亮环。**不新增点类型**（否则图例会膨胀）。

### 数据

- `/api/graph` 支持 `all:true`（等价于新增只读 `/api/nebula`）：每个库返回
  `{id, name, hue, chapterCount, readChunks, wrongCount, artifactCount, lastActiveAt, chapters[], intraEdges[]}`。
- 库内连边沿用现有 `buildGraph` 的聚合（同文档包含 + 章节相邻）；**库间只画一条线**（星云中心 ↔ 中心核）。
  **实现后的调整（2026-10-14，用户看完第一版）**：**团内一条线都不画**——一节一节连出来是一片网，看着乱。
  内核仍然算好 `edges`（`/api/graph` 还在用），只是星云图不画：库里"哪几节挨着"靠点的位置（同文档 = 同一个子团）与颜色表达就够了。

### 实现补充（2026-10-14）

- **团的位置用"空位制"**：球壳上固定 16 个斐波那契空位，库按 id 哈希挑一个（被占就顺延找空的）。
  纯哈希坐标会挤在一侧，而且加库会让整体偏一点；空位制下**新库只占空位、谁都不用挪、颜色也不换**。
- **点击的语义**：星云中心那一坨是"切库/看全局"的把手——中心 8px 内**优先**给中心（不然小库里章节点会把它抢走）；
  章节点 14px 内选中章节，出侧卡（继续学 / 出练习 / 生成讲义）。
- **坐标一致性**：鼠标视差只作用在"画"上，命中测试直接用屏幕坐标比（所见即所点）。
  自检接缝 `window.itnGraphPick(kbId, 章节名)` / `itnGraphPick(kbId)` 返回**画出来的**画布坐标；
  `window.itnGraphInfo()` 回 `{clusters, chapters, perCluster, paintMs}`，性能判据看 `paintMs`（真实重绘耗时），不是 rAF 间隔。
- **实测**：8 库 / 1200 点（每库 150 章）→ `paintMs` ≈ 4.8ms（判据 < 33ms）；5 库 / 20 点 ≈ 0.1~1.2ms。

### 布局（确定性，不跑力学模拟）

- 三层：中心核（1 点）→ 星云中心（每库 1 点，按 id 哈希分布在球壳上；半径按活跃度微调）
  → 章节点（在星云中心附近成团）。
- 团内再分一层：**文档 = 子团中心**，章节按序号哈希散布（半径 1.5~3 倍抖动）→ "星云里有几个亮核"。
- 星云位置按 id 哈希固定，**新增/删除库时不让整体重排**，新库占空位。

### 上限（必须做，否则 canvas 2D 会卡）

- 全局 ≤1200 点；每库 ≤200 点（超出按现有规则折叠成主干 + 标"折叠 N 个"）。
- 库数 >12 只画最近活跃的 8 个，其余折成"其余 N 个库"。
- 未索引/空的库不画星云，画"未成形模糊团 + 建立索引"。

### 交互

- 点中心核 = 全局概览（今天该学什么 / 总进度）；点星云中心 = **切当前库**（同步下拉框与 `state.kb`）；
  点章节 = 现有侧卡（继续学 / 出练习 / 生成讲义）。
- 四档过滤（全部 / 在读 / 错题 / 产物）**跨所有星云**生效。
- 搜索与章节列表作为第二条路径保留（星云只适合看整体，找具体某一节靠搜索）。
- 自检接缝 `window.itnGraphPick` 扩展成 `itnGraphPick(kbId, 章节名)`，E2E 才能点星云与章节。

### 性能与降级

- 呼吸按 20~30fps 重绘，交互时全速；连续 3s 无交互降到 15fps；切页停渲染（现有行为保留）。
- `prefers-reduced-motion`：呼吸静止或周期拉到 20s。
- 浅色/深色两套背景 token（沿用现有主题机制），**不改调色板**。

### 判据

- 12 库 / 1200 点数据下帧时间 < 33ms；
- 点星云中心后，库下拉框的当前库跟着变；点章节能开侧卡；
- `prefers-reduced-motion` 下呼吸静止；浅色主题下点与线不靠发光也能看清（对比度达标）；
- 截图：深色/浅色各一张 + 折叠提示那张。
