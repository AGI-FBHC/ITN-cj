# ITN-Desktop 系统说明

面向仓颉杯综合系统赛道。本文只写已经实测验证过的内容。

## 一句话

把用户自己的资料和用户自己的模型，变成一台在他电脑上出讲义、出练习题的本地 Agent 工作台。

## 解决什么问题

想用大模型辅助教学的人，通常卡在三件事上：资料要上传到别人的服务器；模型回答的内容没法核对出处；生成出来的东西散在聊天记录里，没法版本管理。

ITN-Desktop 的做法是：资料留在本机，只把必要的片段发给用户自己配置的模型；每条结论都带编号出处；讲义和练习直接落成本地 Markdown 文件。

## 技术架构

```text
┌──────────────────────────────────────────────┐
│  Electron 外壳（只做三件事）                  │
│  拉起内核 · 读端口文件 · 把窗口指向本地地址     │
├──────────────────────────────────────────────┤
│  仓颉内核（项目主体）                         │
│  llm · session · tools · agent · kb · store · api │
│  监听 127.0.0.1，端口由系统分配                │
└──────────────────────────────────────────────┘
```

界面文件由仓颉内核以静态资源托管，界面与接口天然同源，不需要处理跨域，前端也没有构建步骤。

## 仓颉的使用情况

整个内核用仓颉 1.2.0 编写，编译目标 `x86_64-w64-mingw32`。

用到的仓颉能力：`stdx.net.http` 提供本地 HTTP 服务，`stdx.net.tls` 承担出网的 HTTPS，`stdx.encoding.json` 处理请求与响应，`stdx.encoding.base64` 把图片编码成多模态消息，`std.fs` 负责目录遍历与文件读写，`std.sync` 的 `spawn` 让服务在后台线程运行，`Random` 生成会话标识。

工程上有三个坑值得记下来，供同行参考。

一是链接：stdx 的证书模块会调用 Windows 证书 API，必须补 `-lcrypt32`，否则出现 `CertEnumCertificatesInStore` 未定义符号。

二是类型：仓颉里 `x as T` 在类层次上返回 `Option<T>`，类型判断应改用 `case x: T =>` 模式匹配。

三是**TLS SNI**，这一条最关键。仓颉的 `stdx.net.http` 客户端不会把请求域名自动带入 TLS 握手，缺少 SNI 时云厂商会直接以 `internal error` 拒绝握手。表现是：同一台机器用其他工具直连该端点返回 200，而仓颉客户端始终握手失败，且把 TLS 版本（1.2 / 1.3）、安全级别（0 / 1）、ALPN 逐个换过一遍，七种组合的错误一模一样。修复方式是显式设置：

```cangjie
var tls = TlsClientConfig()
tls.serverName = Some(hostOf(url))   // 从请求 URL 取出主机名
let client = ClientBuilder().tlsConfig(tls).build()
```

不修这一条，本项目对任何正经云厂商的模型服务都打不通。内核另外提供 `/api/models/diagnose`，会自动尝试多种 TLS 协商参数并报告哪种可用，方便用户自助排查自己的端点。

## 五条主链路

**模型自由配置**：用户自行填写 Base URL、API Key 与模型名，并分别绑定三种用途——对话生成、向量化、切片与图片描述。密钥只存本机，接口永不回传。

**自定义知识库**：指定任意本地目录，递归读取 Markdown 与纯文本。按标题层级分块并记录标题路径作为出处；代码围栏内的内容不会被误判成标题，也不会被切开。

**含图片的多模态切片**：图片引用随所属切片记录，建索引时把图片编码后交给多模态模型生成描述，参与向量化的文本是「正文 + 图片描述」，因此图里的信息同样可被检索命中。这条能力用真实视觉模型验证过：把界面截图放进知识库，模型返回的描述准确读出了图内的中文界面文字，说明链路真实可用，不是桩。

**检索增强问答与内容生成**：提问先检索、再作答，答案带 `[编号]` 出处；讲义与练习同样基于检索结果生成，末尾附「资料来源」章节，逐条对应到文档与标题路径。

**课件播放与画像校准**：讲义、练习册与整章资料都能「按页播放」——按二级标题切页，支持目录跳页、字号放大、全屏与键盘翻页，播放进度写回本机 SQLite 的 `meta` 表（接口 `/api/artifacts/progress`），下次自动续播；「画像校准」用五档自评（20/35/50/65/80）对齐六维能力，并给出真实答题正确率作对照，结果写回档案并可留一条校准记录笔记。

**带工具的 Agent 回路**：提问支持多轮上下文（取最近 6 轮），模型可以在作答前调用本地工具——检索知识库、列出文档、按 id 读原文、看当前时间、算四则运算、写笔记、写产物。工具协议不依赖供应商的 function calling：提示词要求模型"需要工具时只输出一行 `{"tool":...,"args":{...}}`"，内核扫描出这个 JSON 再执行，因此任何兼容 `/chat/completions` 的服务都能跑。正文生成过程中每段正文写一条 `assistant/delta` 事件，界面轮询事件流做出打字机效果（内核 HTTP 服务是多线程的，实测生成期间其他接口 3~34 ms 返回，所以不需要额外的 SSE 通道）。

## 引用自检

生成结束后程序化统计 `citationReport`：正文段落数、带引用段落数、越界引用编号数。这让「可溯源」从口号变成了可测的数字，实测一次问答复核结果为「段落 1 · 带引用 1 · 越界引用 0」。

## 运行方式

绿色压缩包，解压即用。目标机器不需要安装仓颉，也不需要安装 Node。

```text
ITN-Desktop/
  ITN-Desktop.exe        应用入口
  resources/app/         外壳与应用代码
  resources/kernel/      仓颉内核与 4 个必需 DLL
  locales/  *.dll        Electron 自带运行时
```

内核产物约 17 MB（可执行文件 10.23 MB + 仓颉运行时 1.24 MB + boundscheck 0.04 MB + libssl 0.95 MB + libcrypto 5.25 MB），完整压缩包约 162 MB。

## 实测验证

以下都是实际执行结果，不是预期。

技术验证：本地 HTTP 服务可用系统分配端口、`/health` 返回 200、未注册路径 404；HTTPS 出网对 `cangjie-lang.cn` 与 `baidu` 均返回 200；把产物复制到空目录、`PATH` 只留 `System32` 也能正常启动并完成 HTTPS 调用。

真实模型服务验证：用真实供应商端点（`https://token-plan-cn.xiaomimimo.com/v1`，模型 `mimo-v2.6-pro`）发起调用，定位并修复上述 SNI 问题后，`/api/models/test` 返回「连通」（约 3.6 秒），`/api/chat` 拿到真实模型回答——例如提问「用一句话说明什么是提示词」，返回「提示词是用户输入给 AI 模型的指令或问题，用来引导模型生成所需的内容或回答。」。这条链路走的是完整 HTTPS，不是本地桩。

同一次验证还发现：该供应商只提供对话接口，`/embeddings` 返回网关 404。这从侧面印证了「对话 / 向量 / 切片」三种用途必须分开绑定——不能假定一个服务三样都能做。向量链路目前以本地 mock 验证。

功能验证（界面全流程，本地 mock 模型，无真实密钥）：`tools/ui-e2e.cjs` 自起 mock 与内核、用无头 Edge 按用户操作顺序点 **40 步**，全部通过——配模型（预设填入）→ 绑三种用途 → 登记知识库并建立索引（2 篇文档 / 3 个切片 / 1 张图 / 1 条图片描述）→ 读章节并标记已读 → 出题作答（对错反馈、错题入本）→ 生成练习册与讲义（含「资料来源」）→ 在「我的资源」读全文 → 在对话里提问（答案带 3 条出处）→ **Agent 自己调用工具算数**（工具行显示「检索知识库 / 计算：(12+8)*3/4」，回答为 15）→ 点会话栏还原历史对话与出处 → 新建空会话 → 按页播放产物（逐页翻完无空白页、续播到第 5 页）→ 整章按节播放 → 写档案 → 六维校准写回（且不清空昵称与学习目标）→ 生成校准记录笔记 → 会话记录展开 → 写笔记 → 看成长统计，全程 0 条前端报错。

流式与工具验证：一次带工具调用的问答会产生 `assistant/delta` 8 条、`tool/call` 3 次（含自动检索），会话类型标记为 `ask`；`tools/smoke.ps1` 覆盖全部 32 个接口，`study-api-check.ps1` 与 `keyword-mode-check.ps1` 通过。

会话日志验证：一次讲义生成产生 17 条事件，完整覆盖 `turn/start`、`user/message`、`step/start`、`tool/call`、`tool/result`、`validation`、`turn/end` 的生命周期。

打包验证：`dist/ITN-Desktop/ITN-Desktop.exe --smoke` 返回 `TITLE=ITN-Desktop · 本地教培工作台 / STATUS=内核已连接 · 1.2.0 / NAV=11 / VIEW_NODES=6 / RESULT=OK`（NAV 是侧栏导航项数，VIEW_NODES 是首屏渲染出的卡片数；此前这条检查数的是 `.panel`，那个类名早就不存在，等于一直在数 0，已一并修掉）。

## 已知边界

不做联网检索，只用用户自己给的资料和模型。内置的纯仓颉 SQLite 驱动用 `itn.db-cjflock` 做跨进程互斥，但它靠 `/proc` 判断持锁进程是否存活，**Windows 上没有 `/proc`，只能一律认为持锁者还活着**——于是一次强杀（任务管理器结束进程、崩溃）留下的锁文件会让数据目录再也打不开，表现为所有读库接口 500。两层处理：外壳启动内核前用 `process.kill(pid, 0)` 判断并接管残留锁；内核把未预期异常统一转成带原因与处理办法的 JSON，界面上能直接看到"关掉其他实例、删掉 itn.db-cjflock"。知识库当前只收 Markdown 与纯文本，PDF 与 Word 不在范围内。多模态描述依赖用户自行配置一个支持视觉的模型，未配置时只按正文文本切片。英文与其他语言的检索效果未做专门评测。
