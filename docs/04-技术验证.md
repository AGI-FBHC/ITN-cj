# 技术验证记录

三项会卡住方案的前提全部验证通过。以下都是本机实测结果，不是推断。

## 工具链

| 项目 | 版本 / 位置 |
| --- | --- |
| 仓颉 SDK | 1.2.0（cjnative），目标 `x86_64-w64-mingw32`，解压于 `D:\cangjie-sdk\1.2.0\cangjie` |
| STDX | 1.2.0.1 for windows_x86_64_cjnative，静态库位于 `D:\cangjie-sdk\1.2.0\stdx\windows_x86_64_cjnative\static\stdx` |
| OpenSSL | 3.6.5（取自 MSYS2 mingw-w64-x86_64-openssl 包），位于 `D:\cangjie-sdk\1.2.0\openssl\mingw64` |
| 编译器前置 | Visual Studio 生成工具 2022（MSVC 14.44.35207）+ Windows SDK 10.0.26100 |

SDK 官方下载页是单页应用，`preDownLoad` 只是登录校验接口；真实地址形如
`/v1/files/auth/downLoad?nsId=142267&fileName=<包名>&objectKey=<对象键>`，
其中对象键和 SHA256 都在下载页的 JS chunk 数据里。两个安装包均已按官网 SHA256 校验。

## 关键链接参数

```text
-lssl -lcrypto -lcangjie-dynamicLoader-opensslFFI -lcrypt32
```

`-lcrypt32` 不能省。stdx 的 `crypto.x509` 会调用 Windows 证书 API，缺它会出现
`CertEnumCertificatesInStore`、`CertCloseStore` 等未定义符号。

stdx 通过 `cjpm.toml` 的 `bin-dependencies.path-option` 引入，值用环境变量
`${CANGJIE_STDX_PATH}`，由 `scripts/env.ps1` 设置。链接期把 OpenSSL 的 lib 目录放进
`LIBRARY_PATH`，运行期把 OpenSSL 的 bin 目录放进 `PATH`。

## 验证一：本地 HTTP 服务

`ServerBuilder().addr("127.0.0.1").port(0).build()` 由系统分配端口，实测拿到 52161 等随机端口。
`/health` 返回 200 与预期 JSON，未注册路径返回 404。

## 验证二：HTTPS 出网

`stdx.net.http` 配合 `stdx.net.tls` 的 `TlsClientConfig` 实测：

| 目标 | 结果 |
| --- | --- |
| `https://cangjie-lang.cn/`（显式 ALPN http/1.1） | 200 |
| `https://cangjie-lang.cn/`（默认配置） | 200 |
| `https://www.baidu.com/` | 200 |
| `https://www.example.com/` | 握手失败 |

最后一项是本机代理链路的拦截，与本项目代码无关；`TlsClientConfig` 默认配置即可用，不必显式设置 ALPN。

## 验证三：真实 OpenAI 兼容端点（含 TLS SNI 修复）

前三项验证用的是公开 HTTPS 站点，只能证明 TLS 可用，不能证明能打通真实的模型服务。这一项用真实供应商端点做。

**现象**：对 `https://token-plan-cn.xiaomimimo.com/v1` 发起请求，握手阶段直接失败。

```text
TLS handshake failed (client): tlsv1 alert internal error (1080)
```

**排查过程**：先排除网络与凭据——同一台机器用 PowerShell 直连（走系统代理与 `-NoProxy` 两种方式）都返回 HTTP 200，模型正常回复，TCP 443 可达。再逐个尝试 TLS 协商参数，结果**全部失败且错误完全相同**：

| 尝试 | 结果 |
| --- | --- |
| 默认配置 | 失败 |
| 仅 TLS 1.2 | 失败 |
| 仅 TLS 1.3 | 失败 |
| 安全级别 0 / 1 | 失败 |
| 指定 ALPN http/1.1 | 失败 |

错误完全相同，说明不是版本、密码套件或安全级别的问题。剩下的差别是 **SNI**。

**根因**：仓颉的 `stdx.net.http` 客户端**不会把请求域名自动带入 TLS 握手**。缺少 SNI 时，目标服务端无法按域名路由，直接以 `internal error` 拒绝握手。

**修复**：调用前从 URL 取出主机名并显式设置：

```cangjie
var tls = TlsClientConfig()
tls.serverName = Some(hostOf(url))
let client = ClientBuilder().tlsConfig(tls).build()
```

**修复后实测**：

```text
/api/models/test -> {"code":0,"data":"连通"}（3.6 秒）
/api/chat        -> 真实模型回答，例如「提示词是用户输入给AI模型的指令或问题，用来引导模型生成所需的内容或回答。」
```

同一个修复也解释了早期 `www.example.com` 握手失败——当时误判为本机代理拦截，实际是同一原因。

**附带发现**：该供应商只提供对话接口，`/embeddings` 返回网关 404。这从侧面说明「对话 / 向量 / 切片」三种用途必须分开绑定，不能想当然地假定一个服务全都能做。内核已针对这种情况给出明确提示。

内核提供 `/api/models/diagnose`，会自动尝试多种 TLS 协商参数并报告哪种可用，便于用户自助排查自己的端点。

## 验证四：目标机器无需安装仓颉

把可执行文件复制到空目录，用 `PATH` 只含 `C:\Windows\System32;C:\Windows` 的干净环境启动，HTTP 与 HTTPS 均正常。

最小依赖集共约 17MB：

| 文件 | 大小 |
| --- | --- |
| `itn-desktop-core.exe` | 9.55 MB |
| `libcangjie-runtime.dll` | 1.24 MB |
| `libboundscheck.dll` | 0.04 MB |
| `libssl-3-x64.dll` | 0.95 MB |
| `libcrypto-3-x64.dll` | 5.25 MB |

可执行文件只动态依赖 `libcangjie-runtime.dll`，标准库与 stdx 都是静态链入；
OpenSSL 由 `libcangjie-dynamicLoader-opensslFFI` 在运行时动态加载，所以 `libssl` / `libcrypto` 必须随包分发。

## 验证五：知识库规模与内存

小规模知识库（2 篇文档）跑得通，不代表真实规模跑得通。用 100 篇 Markdown（合计 4.2 MB，切出 3500 个切片）配合 1024 维向量做了一次容量验证，暴露出两个问题。

**问题一：内核 OOM 崩溃。** 索引把向量写进 JSON，3500 × 1024 等于 360 万个 `JsonFloat` 对象，直接顶穿内存。运行日志显示：

```text
totalObjSize 85948384 / allHeapSize 268435456
An exception has occurred: Out of memory
```

`allHeapSize 268435456` 说明问题还有第二层：**仓颉运行时默认堆上限是 256 MB**。

**修复**：

1. 向量不再进 JSON。`index.json` 只留元数据，向量单独存 `vectors.txt`，一行一个切片、空格分隔。
2. 写向量文件改为分批追加（`File.appendTo`，每 200 个切片一次），避免一次性拼出几十 MB 的字符串。加载时按字节原地解析浮点，不为每个数字生成临时字符串。
3. 通过 `cjHeapSize` 环境变量把堆上限放宽到 2 GB。这是上限而非预分配，按需增长，需要在启动内核时设置——外壳已经带上，直接跑内核时需自行设置。
4. 索引在进程内按 (数据目录, 知识库) 缓存，重建索引时替换。此前每次检索都要重新读盘并按浮点解析，代价随规模线性上升。

**修复后实测**：

| 项目 | 结果 |
| --- | --- |
| 语料 | 100 篇 Markdown，4.2 MB |
| 切片 | 3500 |
| 建索引 | 10 秒（含 3500 次向量化调用） |
| `index.json` | 4.65 MB |
| `vectors.txt` | 30.76 MB |
| 检索耗时 | 0.28 ~ 0.32 秒（缓存命中） |

## 已知问题

`println` 输出到管道时会被缓冲，进程不退出就看不到端口号。Electron 的端口握手不能依赖标准输出，
后续改为内核把端口写入外壳指定的文件，或找到显式 flush 的方式。
