# 架构与分工

## 运行形态

Electron 拉起一个本地的仓颉进程，两者通过只监听 `127.0.0.1` 的 HTTP 通信，生成类接口用 SSE 逐步返回。对外没有任何服务端依赖。

```mermaid
flowchart LR
  subgraph S["Electron 外壳（薄）"]
    W["窗口 / 系统目录选择 / 打包"]
  end
  subgraph C["仓颉内核（主体）"]
    KB["知识库：扫描 分块 多模态描述 向量索引 检索"]
    AG["Agent harness：循环 工具 会话记忆"]
    MD["模型适配：OpenAI 兼容 文本/视觉/向量"]
    ST["本地存储：配置 索引 会话"]
  end
  W -->|"127.0.0.1 HTTP + SSE"| C
  MD -->|"HTTPS"| API["用户自己配置的模型服务"]
```

## 为什么内核和外壳走本地 HTTP

内核可以脱离 Electron 单独启动和调试，能用命令行直接验证接口，接口契约可以写成文档长期维护。端口交给系统分配，仓颉把实际端口写到标准输出，外壳读取。

## 分工底线

Electron 侧只允许出现三类代码：创建窗口、调用系统文件对话框、打包配置。任何业务判断都不许写在 JavaScript 里，否则仓颉杯的项目性质就说不清楚了。

## 打包

仓颉支持全静态链接，运行时嵌入可执行文件，目标机器不需要安装仓颉工具链。需要随包携带的是 OpenSSL 3 的 `libssl` / `libcrypto` 动态库，因为 HTTPS 客户端依赖它。`cjpm` 自带 `bundle` 可以打包制品。最终产出一个绿色压缩包。
