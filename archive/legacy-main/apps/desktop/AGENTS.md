# ITN-Desktop 协作指引

## 工作约定

1. 每次功能更新都要在本地 Git 提交，方便回滚。不要用 `git reset --hard`。
2. 每次操作与对话要点统一追加到整个仓库根目录 `../../TRACE.md`，只追加不删除，写清时间、范围、涉及文件、提交号、验证结果。本目录原 `TRACE.md` 保留为导入前历史，不继续分叉记录。
3. 终端使用 PowerShell 7（`pwsh`）。
4. 密钥、API Key、`.env` 一律不进 Git。
5. 桌面端 `docs/` 仅本地保存，不提交或推送。涉及接口改动时先更新本地 `docs/02-接口契约.md`，再改代码。
6. 界面功能与 Lumin 工具成对：harness（桌面端）每新增或调整一项功能，都要同步提供 Lumin 可直接调用的工具——用户在界面能做/能看的东西，Lumin 也要能读到，并可等价执行（写操作受确认门槛约束）。新增或修改工具时，核心单测 + mock 端到端各多跑几遍，确认没坏再提交。
7. 测试要讲明白、要有意义：跑任何测试/检查前向用户说明这轮测什么、怎么触发、能抓住哪类问题、哪些覆盖不到；检查必须能捕捉真实错误（先复现再修），不许写只求通过的摆设断言；发现偶发失败要查明是产品竞态还是测试写法问题，并在 report 里说明结论。
8. 技术栈尽量纯仓颉：新增的内核代码、工具、测试夹具一律用仓颉实现（例：批量造数走内核的 --seed-fixture，不再用 Python 直写 sqlite 文件）；只有仓颉确实做不到且没有等价替代时才引入其他语言，并在 TRACE 里写明理由。

## 开发顺序

先验证再写业务：仓颉工具链能编译、能起本地 HTTP 服务、能配好 OpenSSL 走通一个 HTTPS 的 OpenAI 兼容接口、静态链接打包后能在干净环境跑起来。这四件事没过之前不写业务代码。
