# 第三方依赖与工具使用说明

面向仓颉杯综合系统赛道的材料补充。所有版本号均来自本机实际安装的产物。

| 组件 | 用途 |

本地 mock 模型服务（`tools/mock-openai/server.py`）实现了 OpenAI 兼容的对话与向量接口，用于在没有真实密钥的情况下跑通全链路验证。它不是产品的一部分，也不随包分发。

## 二、对仓颉生态的依赖边界

项目的业务逻辑全部由仓颉实现，不依赖任何非仓颉语言的运行时来完成功能。具体分工：

- 仓颉侧：HTTP 服务、TLS 出网、JSON 处理、知识库分块与检索、会话日志、Agent 流程、接口层、界面托管。
- Electron 侧：仅窗口创建、进程拉起、端口读取。不承载任何业务判断。

界面文件虽由 Electron 显示，但由仓颉内核以静态资源方式提供，Electron 只是把它指向本地地址。

## 三、AI 工具使用说明

本项目在开发过程中使用了 AI 编程助手（Codex），如实说明如下。

**AI 参与的部分**：代码骨架、模块实现、文档撰写、测试脚本编写，以及一部分排错过程中的资料检索。

**人工负责的部分**：产品定位与边界界定、技术选型决策、验收标准的确定，以及对 AI 产出的逐项实测验收。

**关键的验证要求**：所有结论都以实际执行结果为准，不以"应当可用"作为完成依据。项目里因此保留了一组可重复执行的验证脚本：

| 脚本 | 验证内容 |
| --- | --- |
| `scripts/build.ps1` | 仓颉内核可编译 |
| `scripts/package.ps1` | 内核可打包为独立分发的目录 |
| `scripts/package-app.ps1` | 产出绿色压缩包 |
| `tools/smoke.ps1` | 接口与四条主链路端到端（自带 mock，无需密钥） |
| `tools/ui-check.ps1` | 界面托管与静态资源白名单 |
| `tools/package-smoke.ps1` | 打包后的应用能真正启动并连上内核 |
| `tools/kb-scale-check.ps1` | 真实规模知识库下的建索引与检索耗时 |
| `tools/real-model-check.ps1` | 真实 OpenAI 兼容端点的对话链路 |
| `tools/tls-diagnose.ps1` | 端点 TLS 协商诊断 |

**AI 出错并被人工复核纠正的例子**，一并记录以示验证的必要性：

1. AI 曾把 `www.example.com` 的 TLS 握手失败判断为「本机代理拦截」。后续用真实模型端点复现同类失败并逐步排查，才发现真正原因是仓颉 HTTP 客户端未设置 SNI。此前的结论是错的。
2. AI 在检索排序中把命中项标记为已取用后返回了同一对象引用，导致分数全部被覆盖成 -2。这个问题在第一次端到端实测中才暴露。
3. AI 曾用 2 篇文档验证知识库，结论"性能良好"。把语料放大到 100 篇、向量维度提到 1024 后，内核直接内存溢出崩溃。规模验证不可省略。

## 四、演示录制建议

如果需要录制演示视频，建议按下面的顺序走，全程约三分钟，不涉及任何真实密钥（可用任意 OpenAI 兼容服务）。

1. 解压绿色包，双击 `ITN-Desktop.exe`，界面直接打开，右上角显示"内核已连接"。强调不需要安装任何环境。
2. 进入「设置」，填写 Base URL、API Key、模型名，点「测试」显示连通；把对话、向量、切片三种用途分别绑定。
3. 进入「知识库」，选一个自己的资料目录，保存后点「建立索引」，等待统计回显（文档数 / 切片数 / 图片数）。
4. 进入「对话与产物」，输入一个问题点「提问」，展示答案与下方逐条出处。
5. 输入一个主题点「生成讲义」，展示 Markdown 渲染结果与文末「资料来源」章节，并指出下方"已生成的产物"列出了落盘文件与完整路径。
6. 打开该 Markdown 文件，说明产物是本地文件，可版本管理、可再生成。
7. 可选：打开 `%LOCALAPPDATA%\ITN-Desktop\sessions` 下的 JSONL，说明每个回答都能在日志里找到当时的检索结果，这是"可溯源"的实现方式。
