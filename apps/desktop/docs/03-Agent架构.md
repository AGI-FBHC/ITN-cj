# Agent 架构：借鉴与取舍

参考对象：Pi Agent（`@earendil-works`，生产级 Agent 运行时）与 DeepSeek Harness（开源，"一切皆插件"）。
只借架构思想，不借源码。实现语言是仓颉。

## 一、从 Pi 借的三件事

### 1. 三层分离

Pi 把系统切成 LLM 通信层、Agent 运行时、产品层，每层只知道自己该知道的事。这条我们直接采用，边界如下：

| 层 | 职责 | 不允许知道的事 |
| --- | --- | --- |
| `llm` | 和模型说话：请求、流式响应、错误归一化 | 不知道什么叫讲义、什么叫知识库 |
| `agent` | 循环、状态、工具调度、会话 | 不知道具体工具怎么实现 |
| 产品层 | 教培场景：讲义、练习、知识库 | 不关心 HTTP 与 SSE 细节 |

这条不是审美偏好。用户能自由换模型是我们的卖点，如果 LLM 细节渗进业务层，换一家模型就要动业务代码。

### 2. 事件流

Pi 自建了一个极简异步可迭代流，生产者推事件、消费者按序消费、最后能取到完整结果。模型的流式响应被标准化成细粒度事件。

我们照做，但只在内部使用：模型返回的字节先归一化成事件（正文增量、思考增量、工具调用增量、结束），再由上层的两类消费者分别处理——界面看实时事件，会话日志看持久事件。

### 3. 流式解析不完整的 JSON

工具调用的参数是边生成边到达的，Pi 不等它完整就实时解析（`toolcall_delta`）。这个细节决定体验：用户能更早看到"正在检索知识库"，而不是盯着转圈等全部生成完。

仓颉的 JSON 解析需要做容错补全，这是内核里一个具体的实现任务。

## 二、从 DeepSeek Harness 借的四件事

### 1. 会话日志是唯一真相

DeepSeek 把 `turn/*`、`step/*`、`user/message`、`assistant/message`、`tool/*` 全部写成只追加的持久事件，运行状态从日志推导。

这条对我们的价值超出"内部实现"：**它正好就是产品的差异化卖点**。用户要的"答案可溯源""产物可复现"，本质上就是"每件事都有据可查"。所以日志落成本地 JSONL，一份会话一个文件，界面上的引用和产物都能追到日志里的那一条。

### 2. turn 与 step 的显式生命周期

定义照搬：

- **step** = 一次模型请求，加上它触发的工具调用。
- **turn** = 零到多个 step。它在领取第一条输入前打开，在不再欠任何工作时关闭。

生命周期钩子：`turn/start` → 组装上下文与工具表 → `pre-step` → `step/start` → 发起模型请求 → 追加消息 → 冻结本次请求的历史视图 → 流式接收 → 工具执行管线 → `step/end` → 还有欠账就再进一个 step → `turn/end`。

"冻结历史视图"这一步很关键：同一 step 内模型看到的上下文必须是不变的，否则边流边改历史会导致行为不可复现。

### 3. 事件分域

DeepSeek 分三类：会话事件（持久）、Agent 事件（在飞的工作）、能力事件（策略接缝）。

我们砍掉第三类。本地单机、用户就是自己的管理员，第一版不需要审批门和沙箱策略。保留前两类，对应到实现就是"写日志"和"推界面"两条消费路径。

### 4. 模式即工具集组合

DeepSeek 提供标准、PTC、极简、创造几种模式，本质是工具集的不同组合。

这个产品表达很适合我们，也直接回答了"什么是 harness"：同一套运行时，换一组工具就是另一种用法。

- **极简模式**：只有检索和回答，验证最小可用。
- **标准模式**：加上讲义与练习生成。
- **（暂不做）实验室模式**：用户自己组工具。

## 三、明确不照搬的

- **全套插件系统**。Cordis 式的运行时装载、patch、profile 与 bundle 组合，单机桌面加短工期撑不起来。我们借"每个部件都是可替换的接缝"这个结构，实现上用接口加注册表，不做运行时装载。
- **多供应商适配层**。Pi 支持二十多家，我们统一走 OpenAI 兼容格式，只做一层适配，不做跨供应商转换表。
- **沙箱与审批策略**。本地应用，不做。

## 四、落到仓颉的模块划分

```text
core/
  llm/       OpenAI 兼容适配：chat / embedding / vision，输出标准化事件流
  session/   只追加的事件日志（本地 JSONL），以及从日志推导运行状态
  tools/     工具注册表与执行管线（pre / execute / post）
  agent/     循环：turn 与 step 的生命周期
  kb/        目录扫描、Markdown 分块、图片描述、向量索引、检索
  store/     本地文件存储：配置、索引、会话、产物
  api/       本地 HTTP 接口，供 Electron 外壳调用
```

## 五、业务实现：循环里到底发生什么

### 两条主线任务

| 任务 | 特征 | 例子 |
| --- | --- | --- |
| 问答 | 快、流式、带引用 | "这几篇资料里对上下文工程怎么说的？" |
| 生成 | 慢、多步、落文件 | "把这块做成一份讲义" |

### 第一版工具集

| 工具 | 作用 |
| --- | --- |
| `kb_search` | 检索知识库，返回切片与出处 |
| `kb_read` | 读某篇文档或某个章节的全文 |
| `outline` | 生成讲义大纲 |
| `write_section` | 按大纲写正文，强制带引用 |
| `quiz_create` | 出题：题干、答案、解析、难度 |
| `artifact_save` | 产物落盘 |

### 引用自检

生成结束后额外走一步：逐条检查论断有没有对应引用，缺引用就补，补不上就删。这是教培场景的刚需，也是"答案可溯源"的兑现方式。对应 DeepSeek 架构里的 validation 概念。

### 上下文治理

知识库文档通常很长，必须在预算内组装上下文：检索结果按 token 预算截断，超长文档分章处理。对应 DeepSeek 的 prompt 组装与 Pi 的历史转换。

### 一次"生成讲义"的完整生命周期

```text
turn/start
  step 1  kb_search      定位相关资料
  step 2  outline        产出大纲
  step 3..n write_section 逐节写正文
  step n+1 引用自检       校验每条论断的出处
  artifact_save          写入 Markdown 文件
turn/end
```

每一步都进事件日志，于是三件事自然成立：界面能显示"正在写第 3 节"；中断后能从日志续上；产物能追回具体资料。

这就是这个 harness 的样子。

## 六、落地情况（2026-10-14 更新）

上面这份架构已经按下面的样子落进 `core/`，与规划的差异一并记在这里。

### 已实现

| 规划项 | 实际实现 |
| --- | --- |
| 只追加的事件日志 | `session/session.cj`，事件存在 SQLite 的 `session_events` 表（不再是 JSONL，加入 `sessions/` 目录的一次性导入） |
| 工具注册表与执行管线 | `tools/registry.cj` 的 `ToolBox` + `tools/tools.cj` 的 `ToolRegistry`，工具定义（`toolCatalog`）与执行分离，界面通过 `/api/tools/list` 读同一份定义 |
| Agent 循环 | `agent/agent.cj` 的 `ask`：`retrieve → 多轮模型调用（可插工具调用）→ 引用自检 → turn/end`，最多 4 轮工具回路 |
| 多轮上下文 | `ask` 会从事件流里取最近 6 轮（12 条消息，单条截断 800 字节且不切断多字节字符）拼进 messages |
| 流式输出 | 每段正文写一条 `assistant/delta` 事件；内核 HTTP 服务是多线程的（实测生成期间其他接口 3~34ms 返回），界面轮询事件即可做出"打字机"效果，不需要 SSE |
| 引用自检 | `citationReport(markdown, sourceCount)` → `{paragraphs, citedParagraphs, outOfRange}`，结果写进 `validation` 事件 |

### 与原规划的两处偏差

1. **工具调用协议不用 OpenAI 的 function calling，改用提示词协议。**
   原规划假设供应商支持 `tools` 字段；实际用户可能接任意 OpenAI 兼容服务（例如只提供 `/chat/completions` 的自建网关，或本次接入的 MiMo TokenPlan）。
   现在的做法是：系统提示词里列出工具清单并要求"需要工具时只输出一行 `{"tool":...,"args":{...}}`"，
   内核按花括号配对扫描出这个对象再执行。任何能输出 JSON 的模型都能用。
2. **工具集与规划不同。** 规划里的 `outline` / `write_section` / `quiz_create` 没有做成模型可调用的工具，
   而是留在 `lecture` / `quiz` 两条**固定流水线**里——它们的步骤编排本身就是产品价值（保证每节都带引用），
   交给模型自由调度反而更不稳定。模型可调的是一组**本地事实类工具**：

| 工具 | 作用 |
| --- | --- |
| `kb_search` | 检索当前知识库，返回带出处的切片 |
| `list_documents` | 列出知识库里的文档与切片数 |
| `read_chunk` | 按切片 id 取完整原文 |
| `current_time` | 本机当前时间 |
| `calc` | 四则运算（自带的递归下降求值器，无外部依赖） |
| `save_note` | 写一条学习笔记到本机库 |
| `save_artifact` | 写一份 Markdown 产物到 artifacts 目录 |

工具结果文本里，检索类结果统一用 `[T1]` 前缀编号，与正文引用 `[n]` 区分开，避免模型的引用编号与界面出处列表错位。

- `tools/ui-e2e.cjs`：25 → 32 步全过，其中包含"Agent 会自己调用工具（算数）"与"流式增量事件真的写进了会话"。
- `tools/smoke.ps1` / `study-api-check.ps1` / `keyword-mode-check.ps1` 全部通过。
- 真实端点：MiMo TokenPlan `mimo-v2.6-flash`（对话、流式）与 `mimo-v2.6-pro`（看图）均实测可用；
